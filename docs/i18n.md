# Adding UI text and languages

This app's UI text lives in two catalogs, `public/i18n/sv.js` (the source of truth)
and `public/i18n/en.js`, loaded by a small runtime (`public/i18n.js`) before every
other frontend script. There is no build step - the catalogs are plain classic
`<script>` files, exactly like the rest of `public/`.

## Add or change a UI string

1. Add the key to `public/i18n/sv.js` **and** `public/i18n/en.js` in the same change -
   `test/i18n.test.js` fails the whole suite otherwise (it checks every key in one
   catalog exists in the other, and that no value is empty).
2. Namespace it next to its section (`connection.*`, `log.*`, `file.*`, `errors.*`,
   ...) - reuse `common.*`/`units.*` for anything generic ("Ja"/"Nej",
   "Hittades inte", "s"/"min"/"h") instead of adding a per-section duplicate.
3. Call it with:
   - `t('namespace.key')` for a plain string.
   - `t('namespace.key', { param })` for interpolation - the catalog value uses
     `{param}` placeholders, e.g. `'Showing the first {shown} of {total} lines.'`.
   - `tPlural('namespace.key', count)` for anything that pluralizes - the catalog
     value is `{ one: '...', other: '...' }`; `Intl.PluralRules` picks the category
     for the active locale, so this is correct even for a future language with more
     than two plural forms.
   Never re-embed the string as a literal, even "temporarily".
4. If the same fact is shown both on the page and in a "Copy analysis" text button,
   don't write it twice:
   - For a `<dl>` section, put it in a `xFields()` list and derive both outputs from
     it - see `field()`/`renderDl()`/`copyFields()` in `shared.js`, and
     `audioFields()`/`connectionFields()` in `app.js` for worked examples.
   - For a section heading that's shown as `<h2>Title Case</h2>` and again as an
     `UPPERCASE` line in the copy text, define it once and call
     `t('namespace.heading').toUpperCase()` for the copy-text line - don't add a
     second catalog key.
   - For anything else repeated between a render function and its copy-text twin,
     pull it into a small shared phrase function (see `startPointExplanation()`,
     `dashRepresentationNotes()`, `yesNo()` in `app.js`) instead of writing the
     translated sentence in two places that can drift apart.
5. A server-side error message: never embed the sentence in `server/`. Give the
   `AppError` subclass (or its call site, via the `override` argument some classes
   take) an `i18nKey` + `params`, and add the matching catalog entry under
   `errors.*` in both locale files. `AppError.message` itself stays English - it's
   a developer-facing fallback for logs and non-browser API consumers (`curl`,
   etc.), never what the browser renders. See `server/errors.js` and
   `errorText()` in `shared.js`, which is what turns `{i18nKey, params, message}`
   into the sentence the user actually sees.

## Add a new language (e.g. German)

The mechanism is additive - adding a language never touches a render function, an
error class, or a test bootstrap:

1. Create `public/i18n/de.js`, copying `public/i18n/en.js`'s structure:
   ```js
   registerCatalog('de', {
     meta: { numberLocale: 'de-DE' },
     // ...every key from en.js, translated
   });
   ```
   Run `node --test test/i18n.test.js` (or add `'de'` to that test's locale loop) to
   confirm nothing is missing.
2. Add `'de'` to `SUPPORTED_LOCALES` in `public/i18n.js`.
3. Add `<script src="i18n/de.js"></script>` to `public/index.html`, right after
   `i18n/en.js`.
4. Add `<option value="de">Deutsch</option>` to `#lang-switcher` in
   `public/index.html`. Language names in the switcher are always the language's own
   native name, written as a literal - never run through `t()` - so a name reads
   correctly no matter which language is currently active.
5. Pick `meta.numberLocale` (`'de-DE'`) so `fmtNumber`/`fmtInt` in `shared.js`
   produce the right decimal-comma/thousands-point convention automatically via
   `Intl.NumberFormat` - no other formatting code needs to change.
6. Run `npm test`. Every suite except `test/i18n.test.js` runs against the `sv`
   catalog regardless of how many locales exist, so adding German only needs that
   one test (plus your own read-through) to confirm completeness.

## Where things live

| File | What |
|---|---|
| `public/i18n.js` | Runtime: locale detection (`localStorage` → browser language → `sv` fallback), `t()`/`tPlural()`, the language-switch wiring. |
| `public/i18n/sv.js`, `public/i18n/en.js` | The two catalogs. One `registerCatalog(locale, {...})` call each. |
| `public/shared.js` | `errorText(err)` (server-error → localized sentence), locale-aware `fmtNumber`/`fmtInt`/`fmtDuration`, `withHint()` (tooltip lookup into `terms.*`), and `claimResults(owner)`/`currentResultsOwner()` (which view a language switch should re-render). |
| `public/app.js`, `public/log.js`, `public/file.js` | Each registers an `onLocaleChange(...)` callback near the bottom that re-renders its view from already-fetched data - a language switch never reloads the page or re-fetches anything, so an in-progress stream log survives it untouched. |
| `server/errors.js` | Every `AppError` subclass: a stable `code` + `i18nKey` + `params`, and an English `message` for logs only. |
